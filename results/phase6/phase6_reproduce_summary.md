# Phase 6 (§6.2) — Reproducibility Summary

Status: `experiments/run_all.py` (`make reproduce`) is built. Its plan was
verified correct via `--dry-run`; a full live `--smoke` pass was attempted
but not completed in this session — see "What actually got verified" below

## What was built

- `experiments/run_all.py` — orchestrates every phase's experiment script in
  dependency order, with `--dry-run` (print the plan, no GPU), `--smoke`
  (every step at drastically reduced scale, for wiring verification only),
  `--from STEP`/`--only STEP` (resume or isolate a step).

## Scope — stated plainly

This regenerates every DATA file (parquet), FIGURE (png), and machine-
generated stats `.md` that some script's own `main()` writes to disk. It
does **not** regenerate the hand-authored narrative documents that
synthesize those numbers into prose (`phase4_pareto_summary.md`,
`phase6_demo_summary.md`, every top-level `phaseN_summary.md`,
`results/demo_deck/rehearsal.md`, this document, etc.). Verified which is
which by checking `grep -rn write_text experiments/*.py` against every
`.md` file that exists in `results/`, rather than assuming from filename
similarity — `phase4_kv_evict_summary.md` (auto-generated by
`phase4_kv_evict.py`) sits next to `phase4_hybrid_summary.md`
(hand-authored) in the same directory with no naming signal to distinguish
them otherwise.

Trajectories are not regenerated (spec §10 — recorded once, committed,
already tracked in `trajectories/`).

Each step's model (primary vs. `--use-fallback`) matches how its
currently-committed output was actually produced: Phase 0/1 on primary
(predates the fallback decision — README's Environment section), Phase 2
onward on fallback.

## What actually got verified, and what didn't

**Verified:** the full 15-step command plan via `--dry-run` — correct
ordering, correct flags per step (cross-checked against every script's own
`argparse` block, not assumed), correct dependency chain (`phase4_pareto_plot`
after both `phase4_pareto_cost` and `phase4_pareto_success`; `demo_deck` and
`cost_model_report` after `phase4_pareto_cost`).

**Not completed:** a live end-to-end `--smoke` run. `gate0_check` (the first
step, primary model) hit a real vLLM startup timeout on the first attempt.
Investigating why surfaced a genuine, separate bug — see "Bug found and
fixed" below — and after fixing it, retries still hit unusually slow/stuck
vLLM boots and, separately, a WSL2 I/O stall affecting even a plain
`pytest -q` (no GPU involved at all), consistent with this project's
already-documented history of occasional genuine process stalls under WSL2
(distinguished from normal slowness by near-zero CPU in "D" state — the
same signature documented in `phase4_pareto_summary.md`'s GPU-thermal-
throttling section for an unrelated earlier stall). The environment
recovered on its own after killing the stuck processes; a narrow retest
(`pytest tests/test_engine_config.py`, then the full suite) passed cleanly
afterward. Given the time already spent chasing what turned out to be
environment instability rather than a defect in `run_all.py` itself, a full
live `--smoke` pass was not re-attempted in this session.

**Data safety:** before attempting the live run, `results/` (git-tracked)
was backed up in full. After the aborted attempt, `diff -rq` against that
backup showed **zero files changed** except one pre-existing cosmetic
whitespace diff in a hand-authored file `run_all.py` never touches — every
step that ran failed or hung during vLLM boot, before reaching the point of
writing any output, so no committed data was ever at risk despite the
instability.

## Bug found and fixed: `VLLMEngine` leaked its subprocess on a failed boot

`VLLMEngine.__init__`'s last line was `self._wait_until_ready(startup_timeout_s)`.
If that raises (server never became healthy, or exited during startup),
`__init__` itself raises — meaning a `with VLLMEngine(...) as engine:` block
never reaches `__enter__`, so `__exit__`/`shutdown()` is never called and
`self._process` (the vLLM server subprocess, holding several GB of GPU
memory) leaks as an orphan. Confirmed concretely, not just theoretically: a
timed-out startup during this session's reproducibility testing left a live
vLLM worker process holding ~6.5GB of GPU memory, which a subsequent boot
attempt then had to contend with — directly worsening, not just coinciding
with, the slowness being investigated. Fixed in
`src/agentkv/serving/engine.py`: `__init__` now wraps
`_wait_until_ready` in `try`/`except BaseException`, calls `self.shutdown()`
on any failure, then re-raises. This matters specifically for `make
reproduce`: without it, any single step's boot failure partway through a
15-step chain would leak GPU memory that every subsequent step then has to
compete for, compounding one failure into several.

Verified: full test suite (172 passed), `ruff check .` (all checks passed),
`mypy src` (33 source files, no issues) — all after the fix, in a healthy
environment.

## Known limitations

- **A full live `--smoke` (or real) run of `run_all.py` has not been
  completed end-to-end.** The command plan is verified correct by
  inspection and `--dry-run`; every individual underlying script has its
  own prior track record of working (their currently-committed outputs
  exist and were produced by exactly these invocations in earlier phases).
  The specific new risk surface `run_all.py` itself introduces — subprocess
  invocation, argument construction, sequencing, resume-on-failure — is
  small, and the one live subprocess invocation that did happen
  (`gate0_check`, twice) correctly triggered and correctly reported
  `run_all.py`'s own failure-handling path each time. But "the plan is
  correct and the failure path works" is not the same claim as "a full run
  succeeds end-to-end," and this document does not conflate the two.
- **`phase4_offload_compare` persists nothing** — it prints its wall-clock
  comparison to stdout only (a pre-existing characteristic of that script,
  not something `run_all.py` changed). `run_all.py` still runs it (so the
  numbers get re-verified/re-printed on each reproduction), but there's no
  file for it to regenerate.
- **This session's environment instability (WSL2 I/O stalls, a slow/stuck
  primary-model vLLM boot) is not fully explained.** The `VLLMEngine` leak
  fix addresses one concrete, confirmed contributing factor; whether
  something else was also going on (Windows-side disk scanning, WSL2
  memory/cache pressure after a long session) wasn't investigated further,
  since narrow retests came back clean and the marginal value of chasing it
  further was low.
